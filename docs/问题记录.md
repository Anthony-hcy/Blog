# 问题记录

本文档记录通过浏览器实际访问本站时发现的问题、根因与修复状态。每次检查追加一节。

## 2026-10-03 站点检查

通过浏览器（Edge + 该站 Service Worker）访问 `https://anthony-hcy.github.io/Blog/` 全面检查，发现以下问题。

### 问题 1：About 页 VIEWS 统计显示 `–`（不蒜子统计失败）

- **现象**：About 页「SITE STATS → VIEWS」显示 `–`。
- **根因**：第三方统计服务 `busuanzi.ibruce.info` 的 JSONP 请求失败——控制台报
  `ERR_CONNECTION_CLOSED` 与 `ERR_BLOCKED_BY_ORB`（Opaque Response Blocking，浏览器
  安全机制拦截了跨域响应）。属于第三方服务不稳定/被浏览器拦截，非本站代码 bug。
- **现状**：`layout.js` 已有 8 秒 watchdog，把占位符降级为 `–`（避免显示误导性的 0），
  降级逻辑本身正确。**保留现状**，不修（第三方服务不可控）。
- **可选项**：若要恢复真实统计，需更换方案（如自托管 umami 或改用其它计数器），
  暂不做。

### 问题 2：「小作文」分类计数不一致（14 vs 15）

- **现象**：主页 / 归档页 / 分类页侧栏显示「小作文 14」，而文章页 / Portal 显示
  「小作文 15」；Portal 侧栏分类合计 37 ≠ 总帖数 36。
- **根因（两层）**：
  1. 仓库曾存在一篇测试文章 `content/posts/post-1790995699522.md`
     （`category: 小作文`，`draft: false`），会参与构建计数；该文件已于
     `919ba9e`（2026-10-03 15:18）删除。删除后全站（含 curl 直连线上）
     分类计数一致为 14。
  2. 浏览器仍显示 15 的根因：`sw.js` navigate 分支误用
     `staleWhileRevalidate`——**先返回缓存旧页面、后台再更新**，导致部署新版本后
     用户继续看到旧页面 / 旧分类计数，直到后台更新 + 版本检查（version.json）触发
     刷新才纠正。而 `sw.js` 顶部注释明确承诺「页面导航：network-first（内容永远最新）」，
     实现与注释不符。
- **修复**：`c138718` 将 `sw.js` navigate 分支改回 `networkFirst`
  （网络可用时永远返回最新内容并更新缓存，断网才回退缓存），与注释一致。
  部署后 curl 与浏览器均应为 14。

### 问题 3：window.load 被懒加载图片延迟约 120 秒，SW 注册被推迟

- **现象**：每次导航等待 `load` 事件超时；控制台提示
  `Images loaded lazily and replaced with placeholders. Load events are deferred.`；
  `performance` 实测 `load_ms` 达约 121 秒。观察窗口内 `sw.js` 请求长时间不出现。
- **根因**：全站图片 `loading="lazy"`，Edge 将 `load` 事件推迟到懒加载图片
  完成；而 `layout.js` 的 SW 注册挂在 `window.load` 上，首访用户在此期间不受
  SW 控制。
- **修复**：`c138718` 将 `initServiceWorker` 的注册时机从 `window.load` 提前到
  `DOMContentLoaded`（模块执行时 DOM 已可交互则直接注册）。

### 问题 4：version.json 首次加载瞬时失败

- **现象**：首次硬刷新时 `version.json?t=...` 报一次 `ERR_FAILED`；随后抓包中
  返回 200（内容 `{"v":"2026-10-03T07:18:33.776Z"}`）。
- **根因**：偶发网络抖动；`layout.js` 的 `initContentRefresher` 已 `catch` 静默
  处理（断网不打扰），且 version.json 请求带 `cache:'reload'`。
- **现状**：无实际影响，不修。

### 可忽略项

- 控制台 `chrome-extension://invalid/` 的 `ERR_FAILED` 来自浏览器扩展（如 iTab）
  的内容脚本，与本站无关。

### 检查结论

- 页面渲染、无限滚动（4 页全加载）、搜索（ExSearch）、PhotoSwipe、字体
  （npmmirror）均正常；本站全部资源 200。
- 需要修复的代码问题为问题 2（SW navigate 缓存策略）与问题 3（SW 注册时机），
  已在 `c138718` 一并修复。

### 问题 5：Portal 发说说「所在位置」被自动回填

- **现象**：手机端打开 `/portal.html` 发说说，「所在位置」里总是已经填好了上次发布用的地点，看起来像自动定位，实际想留空。
- **根因**：`portal-view.js` 的 `newPost()` 会 `#memo-loc.value = readLS(LS.last_loc)` 回填上次位置，`saveMemoMode()` 又在保存时把位置写进 localStorage（`portal_last_loc`）。这是早期「同地点免重复手打」的设计，用久了反而变成默认值。
- **修复**：2026-10-20 去掉回填与写入，位置默认留空；编辑已有说说时仍照常显示该条自己的 `location`。老的 localStorage 键不再被读取，无需手动清理。
- **验证**：手机视口（390×844）预置 `portal_last_loc` 后分别走「Edit 页直接进发说说」和「Posts → New post」两条路径，`#memo-loc` 均为空；编辑已有 memo 时位置仍能正确载入。

### 问题 6：Portal 传图后说说正文写成 `![image](undefined)`

- **现象**：2026-10-20 11:59 用电脑端 Portal「发说说」传了一张图，发出去的说说正文里图片变成 `![image](undefined)`，图片也没进仓库；GitHub Actions 构建直接失败（`裸文件名图片目录不存在` → 构建中止），整站发不出去。
- **根因**：`static/assets/js/portal-view.js` 的 `makePlainJob()` 写成了
  `return [buildEntry(prepared, datedName(ext), dir)];` —— `buildEntry()` 是异步的（内部用 FileReader），
  包成数组时没等它 resolve，于是 `prepareLiveAware()` 收集到的是 **Promise 对象**而不是图片条目。
  这些条目没有 `url` / `name`，`saveMemoMode()` 拼出来就是 `![image](undefined)`，`staged` 过滤也匹配不到，所以图片不会提交。
  该 bug 由 `e05d394`（实况照片改造）引入，影响所有「普通图片」上传：发说说、发文章插图、Images 页上传都中招；只有实况照片（走 `makeLiveJob()`，用了 `Promise.all`）正常。
- **修复**：
  1. `makePlainJob()` 改为 `return buildEntry(...).then(entry => [entry]);`（等真正 resolve）。
  2. `saveMemoMode()` 兜底：只认有 `url` 的图片，全都没有就提示「图片还没准备好，请重新添加」，不再写出 `undefined`。
  3. `useImage()` 兜底：没有文件名也没有地址时直接拒绝。
  4. `scripts/build.mjs` 兜底：`![image](undefined)` 这类字面量坏引用直接丢弃该图并给告警，不再中止整站构建；裸文件名图片解析失败也从「中止」降为「告警 + 原样保留」（单条坏内容不该让整站发不出去）。
- **验证**：本机 1280 视口用假的 GitHub API 跑通「发说说 → 选图 → 确认上传 → 发表」，提交内容为 `![2026.10.20-01](/assets/img/gallery/2026.10.20-01.jpg)` 且图片 blob 一并提交（修复前是 `![image](undefined)` + 0 个图片 blob）；「发文章」插图现在写入 `![[2026.10.20-01.jpg]]`。
- **顺带修好**：11:59 那条说说里的坏图片行已删除（原图当时没上传成功，无法恢复），需要重新传一次。


## 2026-11-20 微信公众平台图片防盗链

### 问题 7：文章 / 封面引用 mmbiz.qpic.cn 的图显示「此图片来自微信公众平台，未经允许不可引用」

- **现象**：`/archives/post-1795174666042/`（《漫步校园，处处皆风景》，转载自公众号）正文 18 张图与首页封面全部变成灰色水印占位图，提示「此图片来自微信公众平台，未经允许不可引用」。
- **根因**：微信图片 CDN（`mmbiz.qpic.cn`）按请求头 `Referer` 防盗链：**带任何第三方 Referer 就返回 200 + 一张 140×140 的占位图**（2090 B、`Cache-Control: no-cache`），不带 Referer 才返回真图（1080×720 webp、`max-age` 很长）。
  实测同一 URL：`curl -e https://haelcy.cn/...` → 2090 B image/jpeg（占位图）；不带 Referer → 89258 B image/webp（真图）。
- **修复**（`scripts/build.mjs`，全站生效，不针对单篇）：
  1. `<head>` 增加 `<meta name="referrer" content="no-referrer">`：全站请求不再向第三方发 Referer，同时覆盖 PhotoSwipe 灯箱里由 JS 动态创建的 `<img>`（这些图拿不到元素级属性，只能靠 meta）。
  2. Markdown 图片渲染器（`renderer.image`）与首页封面 `entryArticle()` 的 `<img>` 显式加 `referrerpolicy="no-referrer"`，双保险。
  3. 注意：微信官方给的 `content="never"` 是旧写法，现代浏览器按无效值忽略，必须写 `no-referrer`。
- **验证**：本机 `http://127.0.0.1:8099` 预览（Referer 为 localhost，等价第三方）：修复后网络面板 12 张图全部 200 且 `mimeType=image/webp`，正文实拍图与首页封面都正常显示；对照页同 URL 不加属性仍是占位图。
- **遗留风险**：图片仍外链微信 CDN，原公众号若删文 / 图片过期，图会 404。要彻底保险得把图下载进 `static/assets/img/<slug>/` 自托管（本站 Portal 的 Images 页可传图）。


### 问题 8：同一篇文章里图片间隙不一致（并排的图 4px、各占一段的图 20px）

- **现象**：`/archives/post-1795174666042/` 里每张图单独成段，图与图之间约 20px 的白缝；而 `/archives/2026.10.21 ——《所有人都在与自己的无价值对抗》/` 里图片两两并排，缝只有 4px，看起来明显不一样。
- **根因**：`scripts/build.mjs` 的 `wrapFigureRuns()` 原来只把「同一段落里连着 2 张以上」的图包进 `.photoset` 相框；单张图仍留在 `<p><figure>` 里，走 `figure.pswp-item { margin: 20px 0 }`。
  相框之间才有 `.photoset + .photoset { margin-top: 4px }` 的 4px 规则，于是「写法不同 → 间距不同」：隔空行各占一段 = 20px，写在同一行 = 4px。
- **修复**：`wrapFigureRuns()` 的正则量词由 `{2,}` 改为 `{1,}` —— 只要段落里只有图片就包成相框（单张也包），所有相邻图片都吃 4px 规则；单张图在相框里仍占满整幅（`flex` 撑满一行，不裁剪）。
- **验证**：重建后该文 17 张图 → 15 个相框（0 个 `<p><figure>` 残留）；本机预览里连续图片缝约 4px；影评文的 2×2 相框排版与修复前一致（仍是并排、4px）。

- **补充（同日）**：图片与文字之间的缝也从 24px 收到 **16px** —— `.photoset { margin: 16px 0 }`，并加 `.article-body p:has(+ .photoset) { margin-bottom: 0 }`（否则段落自身 20px 底边距会和相框外边距折叠成 20px，收不到 16px）。
  实测（620px 宽容器）：文字→图片、图片→文字都从「24px 外边距」变成 16px，屏幕上的空白相应少 8px；图片→图片仍是 4px。


### 问题 9：豆瓣图（doubanio.com）整页裂图 / 首页封面裂图

- **现象**：`/archives/post-1795261822133/`（《安娜》）正文配图与首页封面都不显示；当天早些时候同一张图还是好的。
- **根因（两层）**：
  1. 豆瓣图 CDN 按 Referer **双向**防盗链：**不带 Referer 返回 418**（`img9` 与 `img3` 都一样）；带本站 Referer 时 `img9` 放行 200、`img3` 直接 403。也就是说「带」和「不带」都不保险。
  2. 2026-11-20 为修微信图，全站加了 `<meta name="referrer" content="no-referrer">`，于是豆瓣图变成「不带 Referer」→ 全部 418，原本能显示的 `img9` 也挂了。微信（不带才放行）和豆瓣（必须带）需求相反，referrer 策略治不了两者。
- **修复**：把图下载进仓库自托管。新增 `scripts/fetch-external-images.mjs`：
  - 扫 `banner:` 与正文 `![alt](http…)` 的站外图，按站点选 Referer（微信=不带、豆瓣=`https://movie.douban.com/`、知乎=看 UA），带浏览器 UA 下载；
  - 校验是真图（200 + `image/*` + >1.5KB + 短边 >200px，微信的 140×140 占位图会被挡下）；
  - 存到 `static/assets/img/<slug>/` 并把 Markdown / banner 改成站内路径。
  本次：`p2874549469.webp`（1080×1549，封面）、`p7643185.webp`（691×333，正文）。
- **验证**：本地预览图片请求 200；图有了宽高后还能带 `data-pswp-*`，灯箱与并排布局正常。

### 问题 10：几条独立的 `>` 引用被合并成一个引用块

- **现象**：《安娜》里作者用空行隔开的 5 段引用，页面上变成 2 个引用框（3 段挤在一个框里）。
- **根因**：这些「空行」其实是**只有一个 Tab 的假空行**（从编辑器/微信复制常见）。CommonMark 认为空白行算空行，但 marked 不认，于是引用块继续向下延伸，把后面的 `>` 段都吞进同一个 `<blockquote>`（渲染成 `<blockquote><p>甲</p><p>乙</p></blockquote>`）。
- **修复**：`scripts/build.mjs` 的 `renderMarkdown()` 里先把「只有空格/Tab 的行」统一清成真空行（`replace(/^[ \t]+(?=\r?$)/gm, '')`），引用与段落才按作者写的空行分开。对代码块只是清掉一行空白，无副作用。
- **验证**：重建后该文 `<blockquote>` 由 2 个变成 5 个，页面显示 5 个独立引用框。
