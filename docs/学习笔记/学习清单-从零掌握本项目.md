## 0. 先看懂这个项目（30 分钟，建立地图）

### 0.1 它到底是什么

一个**纯静态个人博客**（没有后端、没有数据库），但发布到**两个地方**，内容完全一致：

| | GitHub Pages（原有） | 自有域名（海外托管） |
|---|---|---|
| 地址 | `https://anthony-hcy.github.io/Blog/` | `https://haelcy.cn/` |
| URL 前缀 | `/Blog` | `/`（根路径） |
| 谁在托管 | GitHub | **Vercel**（海外服务器，**免备案**） |
| 怎么更新 | 推 `main` → GitHub Actions 自动构建部署 | 同一个 push → Vercel 自动构建部署（根路径版） |
| 网页存在哪 | GitHub 的 CDN | Vercel 的边缘网络 |

**关键设计**（这是全项目最核心的一句话）：
> **一份源码、两次构建。** `site.config.json` 一个字不改，靠环境变量覆盖站点地址与子路径：
> `SITE_URL=https://haelcy.cn SITE_BASE=__root__ node scripts/build.mjs`

### 0.2 一次「发文章」到底发生了什么（完整链路）

```
你在 Portal 网页（/portal.html）写 Markdown
   ↓ 用 GitHub Personal Access Token 调 GitHub API 提交
GitHub 仓库 main 分支多了一个 content/posts/xxx.md
   ↓ push 事件
GitHub Actions 触发 .github/workflows/deploy.yml
   ├─ node scripts/build.mjs           → 生成 dist/（Pages 版，前缀 /Blog）
   ├─ upload-pages-artifact + deploy-pages → GitHub Pages 上线
   └─ SITE_URL=… SITE_BASE=__root__ node scripts/build.mjs → 根路径版自检
        + node deploy/check-assets.mjs  → 断言站内引用零缺失
   ↓
同一个 push 也被 Vercel 监听到
   └─ Vercel 用同一条构建命令生成根路径版 → 边缘网络上线（1–3 分钟）
   ↓
GitHub Pages 与 haelcy.cn 同时看到新文章
```

另有**定时任务**：`.github/workflows/fcircle-data.yml` 每天 04:00（北京时间）跑一次，
下载 `fcircle_core` 采集友链 RSS → 生成 `site-root/fcircle-data.json` → 提交回仓库 → 触发上面的部署。

### 0.3 技术栈清单（就是学习清单的目录）

`HTML/CSS/JS` · `Markdown + frontmatter` · `Node.js 构建脚本` · `Git / GitHub` ·
`GitHub Actions（CI/CD）` · `GitHub Pages` · `域名注册 + 实名` · `DNS 解析` ·
`ICP 备案 / 公安备案` · `Ubuntu Linux` · `SSH 密钥与隧道` · `scp / rsync / tar` ·
`nginx` · `HTTPS / Let's Encrypt / certbot` · `阿里云控制台` · `Bash / Windows 批处理 / Python` ·
`PWA / Service Worker` · `HTTP 缓存` · `SEO` · `安全加固`

### 0.4 学习顺序（别跳步）

```
模块 1-2  前端与内容   ┐
模块 3-4  构建与版本   ├─ 先能「本地把站跑起来、能改、能提交」
```

## 模块 2｜Markdown、Frontmatter 与 Obsidian 双链

**为什么必须学**：博客的文章就是 `.md` 文件。`content/posts/*.md` 顶部的
`---` 块（frontmatter）决定标题、日期、分类、标签、封面、草稿状态；
正文里用 Obsidian 风格的双链图片 `![[图1.png]]`，`build.mjs` 会把它们
展开成相框 / 并排图 / 实况照片。

**学到什么程度**

- Markdown 全语法：标题、列表、引用、代码块、表格、链接、图片、脚注

- Obsidian 双链语法 `![[文件名]]`、`![[a.png]]![[b.png]]`（同行并排）
- **两个硬约定**（不满足构建会直接报错中止）：

**项目对应物**：`content/posts/*.md`、`content/pages/about.md`、`content/chronicle.json`、

## 模块 5｜GitHub Actions：自动化 CI/CD

**为什么必须学**：你「推一次、两站同时更新」这件事，完全靠两个 workflow 文件实现。
读不懂 YAML，就等于读不懂这个项目的自动化。

**学到什么程度**

- `.github/workflows/*.yml` 结构：`name` / `on` / `permissions` / `concurrency` / `jobs` / `steps`
- 触发器：`push`、`workflow_dispatch`（手动）、`schedule`（cron）、**`workflow_run`**
  （本项目用它解决「机器人提交不触发部署」这个坑）
- `runs-on`、`uses`（用现成 action）、`with` / `env`、`if` 条件步骤
- **Secrets**：为什么 `if` 里不能直接引用 `secrets`，本项目用「探测步骤」间接判断
- 缓存与产物：`actions/upload-pages-artifact`、`actions/deploy-pages`
- `rsync` 上传 + `--no-owner --no-group` 的原因（别把 runner 的数字 UID 带到服务器）
- cron 时区陷阱：`cron: "0 20 * * *"` = 北京时间次日 04:00

**项目对应物**：`.github/workflows/deploy.yml`、`.github/workflows/fcircle-data.yml`、
`scripts/extract_errors.py`、`scripts/fetch_antibot.py`

## 模块 6｜GitHub Pages 与静态托管

### 15D. 安全（贯穿全项目，最不能省）

**为什么**：清单文档明确写着「服务器 root 密码在聊天记录里出现过，属于弱口令，
请改用密钥登录并关闭密码登录」，还有一条铁律：
**关掉密码登录后私钥丢了只能走控制台 VNC 救援——那条路别关。**

**学到什么程度**

- 凭据分层：私钥（`keys/`，**在仓库之外**）、仓库 Secret、PAT、服务器密码，各自放哪、谁能读到
- 最小权限：PAT 只勾需要的 scope；`authorized_keys` 权限 600；`sshd_config` 关密码登录
- 端口暴露面：只开 22 / 80 / 443；8080 只临时开
- 为什么 `keys/` 必须留在 `.git` 仓库目录之外（放进仓库就等于公开）
- 第三方内容的风险：站里嵌了网易云播放器、360 统计、不蒜子统计，跨域/被拦是常态
